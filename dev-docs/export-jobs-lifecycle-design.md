# GVid ExportJobs Lifecycle and Provenance Design

**Status:** Draft new review object. This amendment resolves the two open P2 findings in [Render Engine Design — Review Decision](render-engine-design-ReviewDecision.md); it is not accepted until its own review reports GO.
**Scope:** ExportJobs submission, replay, lookup, request-ID retirement and authority checks for the Glade gateway and offline CLI. Render planning, graph semantics, preview, source resolution and publication rules remain governed by the render engine and graph schema designs.
**Contract:** Draft ExportJobs version 1 in [render-engine-design.md](render-engine-design.md), [render-graph-schema-design.md](render-graph-schema-design.md) and [gvid_render_graph.taut.py](../ir/gvid_render_graph.taut.py). No production compatibility claim exists for this draft.

## 1. Authority domains and request namespaces

ExportJobs has two distinct authority domains. The Glade gateway accepts only `governed_host` requests. Its stable namespace is `(governed_host, project_id)`; project IDs are never reused after deletion. A new request requires a current project authority incarnation, project read authority for the accepted graph and bindings, and write authority for a host-minted destination reference. The incarnation is delivery authority, not part of the logical export or its idempotency key.

The offline CLI and its optional local Taut machine protocol accept only `standalone_import` requests. Its stable namespace is `(standalone_import, local_import_id, project_id)` in the CLI's durable journal. The CLI allocates every import a new, non-reused local import ID that survives CLI restarts; it does not accept a caller-supplied ID as proof of an existing import. Importing the same portable graph again creates a new import ID. A new request requires that existing journal/import, a validated portable graph and binding manifest, and a local authorized destination reference; it has no Glade incarnation. If its journal/import is missing, the CLI rejects the old import ID instead of recreating it from a request. A Glade asset-resolver bridge does not turn a standalone job into a governed-host job.

Within either namespace, `request_id` is unique for the namespace's lifetime. The durable key is `(authority domain, namespace, request_id)`, not bare `(project_id, request_id)`. The local import ID is a stable namespace identifier, not a credential: local journal access or an authenticated local machine-protocol caller supplies authority. Glade never accepts a standalone branch, and the CLI never fabricates host authority. Exactly one of `authority_incarnation_id` or `local_import_id` is present in submit context and in lookup/status/events/cancel caller context according to the provenance branch. The two identifiers cannot authorize each other.

## 2. Admission, replay and lookup

For submit, the receiving gateway or CLI first authenticates the caller and validates its provenance branch and namespace. For an existing live request record, the current caller must have project/job read authority in the governed domain, or access to the same durable import/journal in the standalone domain. The service checks the accepted-ID index before revalidating an original profile/source or expired destination reference. An identical canonical logical payload returns the original job ID, originating context and `replayed=true` without execution or publication; a changed substantive payload returns `idempotency_conflict`. The canonical payload contains project/graph/sequence, accepted graph and binding revisions/set, exact range, pinned profile identity, original destination reference, destination policy and fallback policy. It excludes only the governed delivery incarnation; the provenance/namespace remains fixed in the key.

For a new ID, governed-host admission requires a current incarnation and host project/destination authority. Standalone-import admission requires the existing local import and local destination authority, with no host incarnation. Both then validate pinned inputs and profile, obtain canonical destination ownership, and atomically persist the immutable request, privileged destination binding, stable job ID and accepted-ID index before acknowledging acceptance. A concurrent claimant for the same key re-reads the winner's durable record and returns replay or conflict; it cannot launch a second job. A failed pre-acceptance validation creates no accepted-ID tombstone. Recovery reconciles a partially persisted admission before any retry is classified as new.

`export.lookup` applies the same current caller/namespace authorization and never starts work. While the full record exists, it returns the original job and durable snapshot after a lost acknowledgement, including across host reopen or CLI restart. It does not revalidate an expired original destination reference or promote an old-incarnation result to the current UI. Unknown and unauthorized requests share `unavailable`; an invalid current governed incarnation or unavailable local import returns `stale_context` without revealing a job. For `unavailable` or `stale_context`, both snapshot and diagnostic ID are null; an authorized `retired_request` likewise has no snapshot or diagnostic ID.

`export.status` uses the same caller branches and returns `ExportStatusResult`: `found` carries exactly one retained `ExportStatusSnapshot`; `unavailable` covers pruned, unknown and inaccessible jobs with no snapshot or diagnostic ID; `stale_context` covers an invalid current caller with no snapshot or diagnostic ID. The caller context is validated independently of job existence before any job lookup. It never reconstructs a lifecycle outcome from a tombstone. The status query and record retirement are serialized so a caller sees either a retained snapshot or unavailable, never a partially deleted snapshot.

`export.events` takes an `ExportEventsQuery` with project, job, cursor and exactly one current governed incarnation or local import ID. The receiver checks authenticated project/job or local-journal authority before replay. Its log carries `ExportEventDelivery` envelopes: `event` has exactly one `ExportJobEvent`, while `unavailable` and `stale_context` carry no event, job context or diagnostic ID and terminate the stream. Unknown, inaccessible and pruned jobs have the same unavailable delivery apart from fields that echo the identical query. The sender rechecks authority at each delivery linearization point; project reopen, import loss or access revocation invalidates the subscription, clears queued events, emits at most a context-free unavailable/stale envelope and closes. Retirement of a job record likewise ends an active stream with unavailable. No event is sent after the revocation or retirement linearization point. A caller can resubscribe under a new current context and the retained cursor rules.

`export.cancel` uses the same caller branches. Caller context is validated independently of job existence. Unknown and inaccessible job IDs both return `unavailable` with no terminal state; a revoked or stale caller cannot learn whether a candidate job exists. `already_terminal` is returned only after job read authority is established. An authorized cancel acknowledgement still means only that cancellation was requested, not that a running tool has stopped.

## 3. Retirement without request-ID reuse

Full job records and event logs may be pruned only after the job has a durably recorded terminal state and all attempt/process ownership, source leases, staging/intermediate artifacts, resource descriptors and destination publication or rollback obligations are reconciled. Queued, preparing, running, verifying and interrupted jobs with unresolved ownership retain their full records regardless of age or quota pressure. A terminal job with pending cleanup also retains its record. Before deleting an eligible accepted job record, the supervisor atomically and durably converts its accepted-ID index entry into a compact tombstone containing the namespace key, request ID, authorization/owner scope and a retired marker. It may retain a payload digest for diagnostics but need not retain destination references, media, credentials, job details or a result snapshot. A crash during conversion recovers either the live record or the tombstone; there is no interval in which an accepted ID is absent. Tombstones survive compaction and restart for the namespace's lifetime. Deleting a project or local import ends its namespace; its ID is never reused, and requests carrying that retired namespace are rejected.

After retirement, an authorized submit using the old ID returns `retired_request`, `job_id=null` and `replayed=false` regardless of payload, without source/destination revalidation, destination ownership or execution. An authorized lookup returns `retired_request` with no snapshot. A caller lacking the original job's read authority gets the normal unauthorized/unavailable result, not evidence that a tombstone exists. A new export must use a fresh request ID. Status, events and cancel for a pruned job are unavailable; the tombstone does not pretend to preserve its historical outcome. Tombstones live in a durable keyed store rather than an in-memory set; a configured storage quota rejects new admissions with `capacity` before acceptance and never evicts accepted IDs silently.

**Journal capacity.** Before accepting a new job, the supervisor reserves a durable accepted-ID/tombstone slot for the namespace lifetime and physically backed journal capacity for a bounded worst-case failure, terminal-state, ownership-cleanup and destination-reconciliation path. The reservation is recorded atomically with acceptance, survives restart and is unavailable to progress history or other jobs. The workflow limits attempt count, live artifacts, owned leases and diagnostic/record sizes; before a new attempt or owned resource can exceed the admitted bound, the supervisor must enlarge its durable reservation or refuse that work and use the existing reserve to fail or interrupt the job. Publication intent and its rollback/completion records have reserved space before replacement starts. A job may not report success until its verified result and publication record are durable.

Progress and nonterminal event history use a separate bounded byte/count budget. The supervisor coalesces progress or expires old events with an explicit first replayable sequence and gap/status recovery; it retains the current state and terminal outcome in the full job record until eligible retirement. Exhausting ordinary journal or event space stops new attempts and uses the reserved path for an actionable capacity outcome and complete process/artifact/destination reconciliation. Reserve slots are released only after terminal reconciliation and tombstone persistence; the permanent accepted-ID slot remains counted. The configured quota admits no job unless all active reservations, retained records and non-reusable ID slots fit. A physical write/fsync failure despite preallocation fails closed: no success or ownership release is inferred, and recovery-required ownership remains until storage is restored and reconciliation is durable.

The accepted-ID record and destination publication intent have independent lifetimes: execution and publication reconciliation complete before a job can retire, and pruning cannot release an unresolved destination owner or erase process/artifact ownership. A later successful export may replace a destination under its explicit policy; an old ID can neither rerun nor replace that newer generation.

## 4. Wire and proof obligations

Add `retired_request` to `ExportSubmitStatus` and `ExportLookupStatus`, preserving their existing numeric values and message field tags. `ExportJobAck` echoes the submitted context when returning a retired status, with no historical job claim. `ExportLookupResult` returns no snapshot for retired status. `export.status` returns `ExportStatusResult` with an optional snapshot only for `found`. `export.events` accepts `ExportEventsQuery` and emits `ExportEventDelivery` envelopes; negative deliveries contain no `ExportJobEvent`. For every unavailable or stale-context lookup/status/event response, optional snapshot/event and diagnostic ID are null. Detailed diagnostics live only in authorized found/event branches; the [reference semantic response validator](../ir/validate_export_responses.py) rejects a negative branch carrying job data or a diagnostic ID. Host adapters must apply equivalent checks before sending responses, and receiving clients validate after Taut decode. Cancel merges unknown and unauthorized into `unavailable`; former cancel numeric codes 3 and 4 are reserved and never emitted. Host semantic validation enforces all discriminated provenance, result and delivery rules; generated bindings do not enforce them.

Conformance must cover: a fresh offline CLI submission and lookup with no host incarnation; a fresh governed submission with a current incarnation and rejection of a stale one; exact replay and changed-payload conflict after host reopen and CLI restart; lost acknowledgement with an expired original destination reference; a job-record prune followed by exact and changed retries that both return `retired_request` without launching work; lookup of the tombstone; an unauthorized caller receiving no tombstone disclosure; and a later destination generation surviving the old request retry. Queued, running and verifying jobs past a prune threshold must keep their recovery records through crash/restart until durable terminal state and all owned resources are reconciled. Current, stale, wrong-branch and revoked callers must be exercised for event subscription, including revocation with events already queued; no event may cross the revocation barrier. Status must encode retained/found, pruned/unavailable, unknown, inaccessible and stale-context without a false snapshot; unavailable lookup/status/event responses must carry null diagnostics and be indistinguishable for unknown, inaccessible and pruned targets under an identical query. Cancel must return indistinguishable unavailable status for unknown and inaccessible jobs. Near the configured journal quota, accept a job, exhaust ordinary capacity, force failure and crash/restart; its reserved path must durably record the outcome, reconcile every owned resource, preserve the accepted ID and reject only new admissions with capacity. Crash injection must cover acceptance, duplicate concurrent submit, live-record-to-tombstone conversion, compaction and restart. Python, Rust and TypeScript bindings and golden wire fixtures must agree on the new request, status and delivery shapes.
