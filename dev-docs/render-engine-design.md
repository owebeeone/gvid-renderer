# GVid Render Engine Design

**Status:** Draft design; the [render-engine review decision](render-engine-design-ReviewDecision.md) is NO-GO. The [ExportJobs lifecycle amendment](export-jobs-lifecycle-design.md) is a separate draft review object and supersedes the ExportJobs admission, replay and retirement rules in this section.
**Scope:** Headless render library, pluggable media tools, asset resolution, and separate Glade and CLI clients.
**Controls:** [renderer requirements](render-requirements.md), [flat graph and Taut design](render-graph-schema-design.md), [ExportJobs lifecycle amendment](export-jobs-lifecycle-design.md), [system architecture](../../dev-docs/gvid-arch.md), and [UI design v2](../../dev-docs/ui-design-v2.md).

## 1. Boundaries and ownership

The project service remains the only authority for accepted edits, graph revisions, binding changes, undo, and persistence. The renderer receives an immutable accepted graph snapshot and immutable binding set. A browser intent goes through the Editor service; neither the core library nor a render tool accepts a browser-authored native command or mutates editorial state. The flat graph stays small and editable in the project/UI model. A render workflow is derived from it and can be discarded.

| Part | Responsibility | Excluded responsibility |
| --- | --- | --- |
| Render core library | Validate render inputs; normalize a sequence or source request; create typed render IR and a workflow; select capable tools; calculate cache identities; execute admitted tasks; return artifacts and evidence. | Taut transport, HTTP endpoints, Glade authentication, CLI parsing, accepted edit authority. |
| Glade integration client | Adapt Taut requests/events to the core, obtain accepted snapshots and bindings, supply Glade asset access, map jobs to host supervision, and publish resource descriptors. | Reinterpreting composition semantics or embedding encoded media in Taut. |
| CLI client | Load a portable graph/package and bindings, choose a resolver and profile, run the same core with a local scheduler, verify and publish an export. | Requiring a Glade process for ordinary local/package rendering. |
| Tool providers | Implement typed media operations using pinned executable or library builds, report support and evidence. | Reading or editing the project graph, resolving user credentials, choosing product semantics. |
| Asset resolver providers | Resolve logical registered assets or bound slots to version-checked source access and leases. | Changing graph meaning or substituting a different asset silently. |

The library may be linked into a host process or run in a supervised sidecar without changing these contracts. A sidecar boundary uses Taut for structured requests, results, cancellation, and progress. The Glade host owns the authenticated loopback HTTP byte endpoint; the core only returns artifact handles and metadata. The command/event gateway owns transport, authorization, and correlation, while the preview service owns the request contract and fidelity policy. The render planner and effect registry own semantic lowering; the job supervisor owns global admission and process lifecycle.

A ready sequence preview is one already composited video resource for all active layers. The Preview service requests composition through the renderer and publishes that resource; the UI displays it and may perform display-only scaling or color presentation, but it does not assemble graph layers or apply editorial effects. Independent source preview remains available before insertion. [The composite-preview ADR](../../dev-docs/adr-sequence-preview-composite.md) updates the earlier UI-compositor path in the system architecture.

## 2. Core API and execution flow

A core request identifies a graph ID and revision, sequence or registered source identity, immutable binding set where applicable, exact half-open time range, profile, fidelity, and request/job ID. A governed-host request additionally carries the current project authority incarnation and accepted delivery evidence. A standalone-import request carries the validated portable graph and binding manifest plus a local import ID; it has no Glade incarnation and makes no claim of current host authority. The two provenance variants are explicit and cannot be coerced into one another. A source preview can name a registered asset version and stream without a graph or binding set. The core accepts validated records corresponding to the governed Taut schema; it does not require a Taut network runtime for in-process calls.

The gateway resolves a named output profile to an immutable profile ID, version, definition digest and complete effective stream/color/audio settings at admission. Prepare receives that pinned definition, not a mutable profile name lookup. Run, retry, verification, cache lookup and publication must use the same pinned definition or reject if it is unavailable or mismatched. The pinned profile and request provenance appear in the result and export record. Host incarnation and local import ID are evidence/context fields, not inputs to the normalized semantic plan; identical validated graph, bindings, profile and capabilities can therefore produce the same plan in Glade and offline CLI.

The principal API has two stages:

1. **Prepare:** Validate schema and graph semantics, resolve and pin source identities and the profile definition, expand the requested output range through effects and source handles, build typed render IR, negotiate providers and intermediate formats, calculate cache keys and resource estimates, and return a workflow with actionable diagnostics. No media job starts on an invalid workflow.
2. **Run:** Submit workflow tasks to an injected scheduler, consume version-checked asset handles, reuse verified artifacts where keys match, run providers under cancellation and enforceable resource grants, verify outputs, and return an evidence-bearing result. Publication of a final destination happens only after final verification.

The workflow is a dependency DAG of typed tasks. Each task records its exact input and output time domains, format, semantic operation version, temporal handles, dependencies, resources, provider choice, and expected artifact identity. It is not serialized as the editable project or treated as a native command line. The same planner handles a single frame, a short preview range, and a complete export; the task selection and admission policy differ. A hardware failure never mutates a prepared task's provider identity in place: if policy permits fallback, the planner creates a new attempt for the remaining workflow with the software provider manifest and recalculates that task's and all dependent artifact keys before any fallback output is consumed. The failed attempt's partial artifacts are invalid and cannot seed the successful attempt's cache.

For a seek near the end of a sequence, planning walks backward from the requested output frame or range through only contributing layers and effects. It includes decoder preroll, transition handles, audio filter state, and source timing dependencies, then schedules the requested visible result before bounded adjacent prefetch. It never makes sequence-start rendering a prerequisite unless a declared effect truly requires earlier state. Batch planning can partition a full range, share valid subresults, and assemble only after boundary semantics and verification are satisfied.

The core returns a result containing request context, actual range/time, exact or proxy fidelity, artifact handles, selected provider/build manifest, source fingerprints, warnings, diagnostics, and verification evidence. A Glade client maps this to Taut results and resource descriptors; a CLI writes a file and export record. Cancellation is best effort for a running native process, but stale results never become current UI resources or published exports.

## 3. Pluggable render tools

Start with a pinned FFmpeg/FFprobe provider and a software reference path. The provider interface must allow later libav, GStreamer, MLT, hardware, or specialist implementations without changing graph semantics. Registration can initially be static in the application build; any future dynamically loaded provider must be host-approved and version-pinned. An arbitrary executable path from a project file is never a provider registration mechanism.

Use one small common provider contract plus typed operation capabilities. A provider advertises a stable ID, build/configuration, supported operation and semantic versions, input/output formats, exact or proxy fidelity, temporal handle requirements, deterministic behavior claims, resource needs, and available hardware paths. It assesses a typed task before selection, then executes only tasks it accepted. Narrow capability implementations may cover probing, decode, timed cuts/retiming, video composition and transitions, color conversion, audio gain/envelopes/mixing, encoding, muxing, and final verification. A provider need not implement every operation.

The language-neutral shape is:

    RenderTool.descriptor() -> ToolDescriptor
    RenderTool.assess(TypedTask, HostCapabilities) -> Supported | Unsupported(reason)
    RenderTool.execute(TypedTask, InputHandles, ArtifactSink, TaskContext) -> TaskEvidence | ToolError

    AssetResolver.resolve(ResolveRequest) -> ResolvedAsset | ResolveError
    SourceAccess.open_range(exact_source_range) -> byte stream or seekable handle
    SourceLease.refresh() / release()

TypedTask carries a semantic operation ID and version, validated parameters, exact time conversion rules, requested fidelity, and accepted intermediate media formats. TaskContext carries cancellation, progress reporting, a resource grant, and a diagnostic correlation ID. ToolError has stable categories such as unsupported semantics, missing input, changed input, expired access, capacity, tool failure, and invalid output. The adapter may attach native stderr to a protected diagnostic record, not to the portable graph.

The effect registry defines what an operation means and how it lowers to tasks. Tool providers implement that meaning; they cannot redefine it through hidden defaults. For example, an audio fade task identifies the source/timeline domain, half-open fade interval, exact gain endpoints, curve and curve version, channel behavior, sample rounding, and treatment at cut boundaries. A video fade or dissolve similarly fixes layer order, alpha/color space, interval, and boundary samples. A provider must advertise support for that semantic version or reject it. Unsupported effects cannot become an approximate export by accident; an allowed proxy must be declared in the result.

Provider selection validates an entire decode/filter/encode path and compatible intermediate formats. If conversion is needed, it becomes an explicit typed task with color, channel, sample-rate, and timing rules. Hardware fallback to the software reference path follows the request policy and the new-attempt rule in section 2, and is recorded. FFmpeg is invoked directly without a shell, using arguments or filter scripts built from validated typed tasks; provider executables and builds are pinned or probed by the capability service. The core records the actual provider choices in every export and cache identity.

Provider conformance fixtures must compare the same fade, mix, transition, and boundary range through the reference provider and each candidate provider at declared exact/proxy tolerances. Verification checks output streams and timing after muxing, not merely process exit status.

## 4. Asset resolution and Glade-only sources

The graph contains logical slots and expected media properties, never paths, URLs, tokens, or credentials. A separate immutable binding set names registered asset versions, selected streams, fingerprints, and substitution policy. Resolution is a distinct runtime step. A ResolveRequest names either a bound slot or an independently registered asset version for source preview, plus purpose (preview, export, probe, packaging), required source range and access capabilities.

ResolvedAsset contains verified identity/fingerprint, selected stream metadata, a SourceAccess handle, access characteristics, and a lease. Access characteristics state whether random seeking and byte ranges are supported, whether a stable local file can be supplied, whether bounded materialization is permitted, and when access expires. The resolver may be local-file, portable-package, or Glade-backed. The tool provider sees only SourceAccess or a validated staged file; it never receives a Glade credential or learns how the asset was registered.

Glade may be the only place that knows where an asset came from or how to authenticate to it. The Glade resolver therefore maps the privileged asset registry entry to an opaque, authorized source handle, maintains or renews its lease, and reports source availability and stream metadata through the existing MediaCatalog/AssetBindings contracts. It must detect a changed version or fingerprint before execution and while consuming an export. The request pins the immutable version; a change fails the job or requires an explicit new binding set. It cannot silently use a proxy, another URL, or another registered asset.

Some tools require a seekable filesystem path. A staging adapter may materialize the required source range or whole source only when the resolver allows it, after checking identity, free space, and bounded quota. It validates the staged bytes, marks ownership in the durable job record before writing, cleans temporary material on cancellation/expiry or startup reconciliation, and keeps credentials out of logs and manifests. Interrupted reads do not become valid staged sources; a lost lease must be renewed against the same pinned version or fail. Interactive late seeks prefer range-capable access and local range artifacts; they must not silently trigger a full Glade-source download before yielding a frame. If a source cannot support the requested range within policy, the result is an explicit unavailable/slow-path status that the UI can show.

A portable graph can be shared without source bytes. A portable render package may additionally contain explicitly included, content-addressed source media and a binding manifest; export must respect source access and redistribution policy. The standalone CLI first resolves local paths or package content against the manifest fingerprints. A Glade-only source has two supported paths: an explicitly materialized authorized package, or an optional Glade resolver bridge configured by the user and authenticated at runtime. If neither is available, the CLI reports the missing logical asset/version and a way to supply or package it. A shared graph remains inspectable even when its assets cannot yet be rendered. No credential or machine-local locator is exported with the graph.

## 5. Separate clients and delivery

**Glade integration.** The Glade client obtains accepted snapshots, binding sets, catalog records, and resource grants from their owning services. It translates governed Taut preview/export/cancel/release messages to core calls and publishes Taut progress and result messages with the same request, revision, binding, and authority context. It rejects stale requests before execution where possible and stale results before presentation. The host maps a ready frame or finite preview segment artifact to a leased opaque resource descriptor. The authenticated loopback HTTP endpoint serves only its encoded bytes, including byte-range requests over a complete seekable artifact; it does not expose command APIs or machine paths. The Glade job supervisor schedules preview fairly against exports and releases resources when viewers replace, close, or expire.

**ExportJobs Taut contract.** The draft schema declares submit, lookup, events, status and cancel methods. Submit carries an idempotent request ID, project/graph/sequence, explicit governed-host incarnation or standalone-import provenance, accepted graph revision, immutable binding-set ID/revision, exact range, pinned profile ID/version/digest, opaque authorized destination reference, explicit fail-if-exists or replace-existing policy, and fallback policy. The Glade gateway accepts only governed-host provenance, validates read authority for the pinned project state and write authority for a host-minted destination reference, and rejects expired references for new work; the local CLI accepts only a validated standalone import and local destination reference. Credentials stay out of portable graphs, renderer workers, durable journal records and result messages. The receiving supervisor atomically records the immutable request, its privileged destination binding, stable job ID and durable provenance-scoped accepted-ID index before acknowledging acceptance. A stale governed incarnation cannot start new work. A previously accepted job may finish after reopen under its pinned inputs, but its old-incarnation result cannot become the new UI's current result.

An authorized lookup by provenance-scoped project/import namespace and request ID returns the original job ID, immutable originating context and durable status while the full job record is retained, including after a lost submit acknowledgement or project reopen. Governed callers need a current project incarnation and project/job read authority; standalone callers need access to the same durable local import and journal, without a host incarnation. Unknown and unauthorized requests share an unavailable response. The lookup never restarts work or revalidates an expired original destination reference. The accepted-ID index outlives the full export record as a compact tombstone for the namespace lifetime; a previously accepted ID cannot silently become new work after record pruning or log compaction. Submit idempotency uses a canonical logical payload containing project/graph/sequence, accepted revision, binding set and revision, exact range, profile ID/version/digest, original destination reference, destination policy and fallback policy; it excludes only the governed delivery incarnation. After provenance-specific current-caller authorization, an existing live request ID is compared with that stored payload before profile/source revalidation, destination-reference expiry or destination-owner acquisition. An exact replay returns the original job and originating context without another publication; a changed substantive field returns idempotency-conflict. A retired ID returns retired-request without a job or execution. A new governed ID requires a current project incarnation and host destination authority; a new standalone ID requires a validated local import and local destination authority, with no host incarnation. The CLI's local durable journal supplies the same lookup and tombstone protection across its own restarts. The [ExportJobs lifecycle amendment](export-jobs-lifecycle-design.md) defines the namespace, authorization and retirement sequence precisely.

Events form a retained per-job Taut log with contiguous event sequence, first replayable sequence, ready/heartbeat/transition/recovery-required kinds, bounded subscriber queues and an explicit gap response. Every event and status snapshot echoes request, job, project, graph, provenance and its host incarnation or local import ID, graph revision, binding set and profile identity. Progress may be coalesced but event sequence remains contiguous; terminal success, failure and cancellation are durable and queryable after reconnect while the full job record is retained. Once pruned, only the accepted-ID tombstone remains queryable by request ID. Clients ignore stale/duplicate events, refresh status after a gap, and never infer success from an acknowledgement or process exit alone. Cancel names the job and a command ID, is authorized for that job, and acknowledges only the request to cancel; a terminal event reports the outcome. Cancel of a different job or already-terminal job cannot change it. Export result identifies a verified export record, destination generation and typed output probe summary, not a raw path or media bytes. The optional CLI machine protocol uses these same Taut shapes with local import provenance; a human terminal display is not a structured component boundary.

**CLI.** The CLI loads and validates a graph or package, chooses an explicit sequence/range/profile/binding manifest and asset resolver, invokes the same prepare/run API, and writes a verified output plus evidence record. It has its own local scheduler, durable job journal, startup reconciliation and cancellation handling. Human-facing terminal progress is a presentation concern; any structured process-to-process CLI mode uses the governed Taut messages and wire. The baseline CLI runs offline with local or packaged assets and does not import Glade service dependencies into the core. Optional Glade access is an asset-resolver plugin, not a second render implementation. Imported snapshots use standalone provenance, never a fabricated Glade authority incarnation.

Both clients must produce the same normalized semantic plan for the same graph, binding set, profile, range, fidelity and capability set. Different provider choices or machines may produce different encoded bytes within declared tolerances; provenance and verification make those differences visible. A preview artifact is disposable and cannot be published as a final export without the requested final profile and verification.

## 6. Cache, failure, and evidence rules

Every bound consuming request, result and artifact-use record includes binding-set ID and revision as well as content fingerprints. The consuming artifact identity additionally includes the contributing subgraph semantic digest, graph/effect schema versions, selected streams, exact range and handles, pinned profile ID/version/definition digest and effective settings, fidelity, color/audio policy, actual provider/build and intermediate format versions. A binding-only rebind creates a new consuming identity even for same-byte media while leaving the graph digest untouched. Content-addressed subresults may be mapped across binding sets only after validating every contributing slot's version/fingerprint, stream and semantics against the new request; the mapping records both source and consuming set IDs, and an unrelated-slot rebind cannot silently relabel a final result. An artifact is reusable only after its metadata and bytes validate against the consuming request. Failed, partial, or mismatched artifacts are misses, never successful outputs.

The scheduler accepts resource estimates from the workflow and owns CPU, memory, I/O, disk, and accelerator admission. Estimates are not limits: the supervisor meters actual use and enforces per-job and aggregate native-process memory/CPU/I/O limits, bounded decode queues, and artifact-sink/staging disk quotas. Native tools write only into a metered spool; the supervisor observes process-tree use and spool growth, applies backpressure where safe, and otherwise terminates the attempt with a capacity diagnostic. For every resource class that could block interactive service, an admitted export requires either a hard enforceable limit or supervisor preemption/termination within a measured finite deadline that protects a late seek. Reducing concurrency alone is insufficient. If neither mechanism exists on a host, the supervisor rejects or defers export admission while interactive service must be available; an exclusive batch-only mode may run only when no interactive reservation is promised. Exceeding a grant cannot borrow the preview reservation or grow queues and files without bound. Preview work has bounded priority over long batch work; exports retain fair progress. Every task and result carries job/request correlation.

The Glade job supervisor and CLI local supervisor persist job ID, pinned input/profile/provider context, attempt ID, state, process identity and ownership of staged/intermediate/candidate artifacts before launching or writing. Native processes run in a supervised process tree that is terminated with its owner where supported. On startup, a supervisor checks the recorded process identity and creation token before terminating a verified orphan, so a reused PID cannot target unrelated work. It then reconciles owned paths: incomplete artifacts are invalidated and removed or retained only if independently verified for safe reuse; expired source leases are discarded; a job becomes interrupted/failed with a diagnostic or explicitly resumes from verified tasks. A process exit cannot alone mark success. On normal cancellation or failure, the core releases source leases and staging and the host reclaims resource descriptors.

Final candidates are probed against the pinned profile and timing in the metered spool. Publication requires a destination with an atomic replacement mechanism and a canonical identity shared by Glade and CLI supervisors; aliases that cannot be proven to identify the same destination make admission fail. A shared filesystem/OS publication coordinator in the core uses a cross-process lock and durable per-destination intent. It obtains one exclusive owner for that identity before admitting a job and holds ownership through success, failure or startup reconciliation. A crash may release the OS lock, but the unresolved durable intent blocks a new owner until reconciliation under that lock. A competing active request returns destination-busy without launching another export. A later request may replace an existing result only under its explicit replace-existing policy; its export record names its new destination generation and the generation it replaced, so an earlier success remains historical rather than claiming to be the current destination.

Under that owner and expected destination generation, the supervisor durably records verified candidate identity and publication intent before replacement, retains a uniquely owned prior destination backup for rollback until the export record is committed, and records the committed result before deleting the backup. Startup reconciliation compares final bytes, expected generation and journal: it completes a verified publication record or restores the prior destination only while the interrupted transaction still owns that generation. It never restores a backup over another committed generation. The owner is released only after reconciliation reaches a terminal state. A partial candidate never replaces the final file, and a crash cannot turn an unverified file into a successful export. Logs and records identify source fingerprints and provider builds without exposing source credentials or raw media content.

## 7. Initial implementation slices and proof points

1. Define core request/result, typed task/workflow, SourceAccess/AssetResolver, RenderTool, and scheduler/artifact-store interfaces. Build a graph fixture that plans a late frame and a full export without any network runtime.
2. Implement local and package resolvers, pinned FFmpeg/FFprobe provider, software reference operations and final verifier. Expose an offline CLI using the shared core.
3. Implement the Glade integration and resolver, Taut request/result mapping, lease-aware HTTP artifact publication, and host job supervision. Keep Glade credentials entirely inside the integration/resolver boundary.
4. Add conformance cases: offline CLI import without a host incarnation and Glade plan parity; two-layer preview as one leased composite whose decoded pixels match a reference at a specified time/fidelity tolerance, using independently recognizable overlapping layers and negative controls for omission and wrong order; late seek without whole-sequence rendering; audio fade and video dissolve at range boundaries; same-byte, changed-byte and unrelated-slot binding changes with consuming identity and checked subresult reuse; hardware failure after Prepare with new-attempt keys; pinned profile change between Prepare/Run/retry; missing Glade-only asset offline with an actionable error; authorized package or bridge resolution; cancellation and lease cleanup; changed source during export; final output verification.
5. Exercise the ExportJobs Taut contract across Python, Rust and TypeScript for concurrent jobs, idempotent retry, out-of-order events, cancel-one-job, reconnect/gap recovery, lost accepted acknowledgement followed by request-ID lookup after reopen, changed-payload conflict and old-incarnation results. Prove new governed and offline standalone admissions with their distinct authority checks. Prune a full export record, then retry its request ID and verify a retired-request response, no new job and no overwrite of a later destination generation; test unauthorized lookup without tombstone disclosure. Crash the Glade host and CLI at admission, live-record retirement, staging, intermediate, verification and publication boundaries, then check durable status, orphan cleanup or verified resume and destination preservation. Run two jobs against one canonical destination, including path aliases and crashes at each publication boundary; prove one active owner, typed busy response and no rollback over another committed generation. Underestimate memory, disk and I/O needs with one export while seeking, including hosts without a hard limit, and prove bounded preemption or an explicit capacity/defer outcome with fair exact-frame progress.

The first implementation should pin precise audio fade curves, transition/color semantics, supported source-access modes, and profile set before claiming provider parity. The exact dynamic plugin loading policy and remote-source bridge protocol can be decided after the in-process interfaces and offline CLI prove the boundary.
