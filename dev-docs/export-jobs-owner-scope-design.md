# ExportJobs Owner-Scoped Request Namespace Design

**Status:** Draft new review object. This proposal resolves the open submit-disclosure finding in the [ExportJobs lifecycle review decision](export-jobs-lifecycle-design-ReviewDecision.md). It is not accepted until its own review gate reports GO.
**Scope:** Governed-host ExportJobs request identity and authorization. It amends the namespace, submit, replay, lookup, and tombstone rules in [ExportJobs lifecycle and provenance design](export-jobs-lifecycle-design.md), [render engine design](render-engine-design.md), [graph schema design](render-graph-schema-design.md), and the draft Taut wire. The offline CLI import namespace, render plan, media bytes, destination publication, and journal reserve remain governed by their existing drafts.
**Compatibility:** ExportJobs is a draft version 1 contract with no deployed reader or writer. The new optional wire fields are required or forbidden by provenance-specific semantic validation; their optional encoding preserves the existing field tags. No production compatibility or migration claim is made.

## 1. Authority partition

The governed project authority mints a stable, opaque `owner_scope_id` for each export ownership domain in a project. It is unique within that project, never reassigned to a different ownership domain, and never reused while the project namespace exists. It is an identifier, not a secret or bearer credential. A caller supplies it to select a domain, and the Glade gateway checks the caller's **current** authenticated project and owner-scope grant before consulting an accepted request-ID index. The current project authority incarnation remains a separate delivery check; it is never an idempotency-key component.

A grant to submit exports under one owner scope also grants read visibility to **every accepted export ID and job in that scope**, including live records and tombstones. The host must not issue a submit grant for a scope while imposing a narrower per-job read restriction within it. A collaborator who needs private jobs uses a distinct scope. Delegation or transfer to another principal is explicit and conveys the same historical visibility; project membership, graph read access, or destination write access alone does not transfer the scope. Revocation stops further caller access but does not cancel an accepted job or erase its durable ID. A retired scope cannot accept new work; its accepted IDs remain reserved until project deletion. Deletion ends the project namespace, and neither project nor owner-scope IDs are recycled.

This partition is the privacy boundary: a caller authorized in a scope may observe its own collisions, replays, conflicts, and retired IDs. A caller outside it cannot probe its request-ID occupancy. Status, event, and cancel requests by globally unique job ID keep their existing unknown/inaccessible indistinguishability and recheck current job/scope authority. A renderer worker never receives owner-scope grants or credentials.

The standalone CLI keeps `(standalone_import, local_import_id, project_id)` as its authority namespace. Access to that durable import/journal covers its accepted jobs. The CLI has no governed owner scope and never invents a host one, even when an optional Glade asset resolver supplies bytes.

The host keeps current grants, scope-retirement state, the accepted-ID index and job records under one per-scope durable serialization order. A preliminary grant check may reject early, but cannot authorize a later request-ID or job-ID classification, mutation or response by itself. Revocation and scope retirement advance that order. Governed replay, conflict, tombstone, lookup and job-ID status/cancel classification recheck the current grant under the same fence. New-key admission and cancel action recheck it at their durable commit points; a retirement ordered before admission or a revocation ordered before cancellation prevents the effect. A response carrying a job or index-derived fact is gated again when its frame is handed to the transport under the same fence; queued responses are suppressed if revocation ordered first. A frame already handed off before revocation may arrive later, but no new positive or index-derived frame may be handed off afterward. A fence may be implemented by a serializable transaction, lock or durable authority version, but stale caches and an earlier gateway check cannot substitute for it. Reopen and restart preserve the ordering and revoked state.

## 2. Durable identity and submission order

The governed accepted-ID key is `(governed_host, project_id, owner_scope_id, request_id)`. The standalone key remains `(standalone_import, local_import_id, project_id, request_id)`. An owner scope is therefore part of the durable key, not part of the portable graph or semantic render-plan digest. Different governed scopes may use the same human-visible request ID without colliding. Their jobs still contend for one canonical destination under the existing publication coordinator and explicit destination policy.

For governed submit, the gateway authenticates the caller, validates the current project incarnation and provenance branch, then resolves and authorizes the supplied owner scope **independently of the request ID and proposed render payload**. An unknown, retired, or inaccessible scope returns `unauthorized` for every candidate request ID: the exact echoed caller-supplied context and contract version, null job ID, `replayed=false`, and null diagnostic ID. An invalid current incarnation returns `stale_context` independently of request-ID occupancy. Neither branch consults the accepted-ID index. The response is also checked against the originating request before send and after decode; it may not echo a resolved job context. The host does not disclose whether an owner scope exists to an unauthorized caller.

Only after owner-scope authorization under the shared fence does the host look up the scoped accepted-ID key. The scope grant itself supplies read authority for any matching live job or tombstone. An exact logical replay of a live job returns the original job and originating context without rechecking the original profile/source or expired destination reference. A changed substantive payload returns `idempotency_conflict`. A retired ID returns `retired_request` with no job or execution, regardless of new payload. The canonical logical payload is the existing pinned graph, binding, profile, range, destination and fallback record; it excludes the delivery incarnation. Scope is fixed by the key. These outcomes reveal accepted-ID occupancy only to a caller authorized at classification and disclosure.

A new key then passes the existing graph, binding, source, profile, destination-write, capacity and canonical-destination-owner checks. Admission atomically persists the immutable request, privileged destination binding, stable job ID, scoped accepted-ID index and durable journal reservation, with a final current-grant and active-scope check in the shared serialization order, before acknowledging it. A concurrent claimant for the same scoped key rereads the durable winner and returns replay or conflict; it cannot start another attempt. Failure before durable acceptance leaves no accepted-ID tombstone. A collision in another owner's scope is irrelevant to this key, though canonical destination ownership can still reject or serialize the new job.

Full-record pruning, atomic live-record-to-tombstone conversion, permanent accepted-ID retention, bounded journal reserve and restart reconciliation follow the lifecycle amendment. The tombstone includes the owner scope in its key and authorization scope; it does not gain a new lifetime merely because a principal is revoked or an owner scope retires. An inaccessible accepted ID never becomes available to another scope via scope reassignment.

## 3. Wire, lookup and delivery

`ExportJobContext.owner_scope_id` is a new optional Taut field, tag 14. A governed context requires a nonempty, host-minted owner scope and a host incarnation, with null `local_import_id`. A standalone context requires null `owner_scope_id` and host incarnation and a nonempty `local_import_id`. The owner scope is echoed in authorized acknowledgements, events and snapshots through the context, but is delivery/authority metadata, not graph semantics.

`ExportLookupQuery.owner_scope_id` is a new optional field, tag 6. Governed lookup requires it and a current caller incarnation; standalone lookup forbids it and requires the local import ID. `ExportLookupResult.owner_scope_id` is an optional tag 7 that echoes the query scope, including negative results. Query echo is caller-supplied context, never a resolved owner name or job fact. The receiver authorizes the scope with the index read under the shared fence and gates disclosure after any revocation. Unknown and inaccessible scopes/IDs return identical `unavailable` envelopes for an identical query, with null snapshot and diagnostic ID. An invalid current caller returns `stale_context` independently of ID existence. An authorized retained record returns `found`; an authorized tombstone returns `retired_request`.

`export.status`, `export.events` and `export.cancel` continue to identify a globally unique job ID and current caller provenance. Internal job-ID routing may locate the owning scope but cannot expose that fact before authority is checked. Governed status classification and snapshot read, and cancel classification and durable command action, share the scope fence with revocation. Their found/already-terminal responses pass the same transport-handoff gate. If revocation orders first, status and cancel return the ordinary inaccessible `unavailable` envelope with no snapshot or terminal state, and cancel has no effect; unknown IDs produce the same envelope. A cancellation durably committed before revocation may still take effect, but a pending positive acknowledgement is suppressed if revocation precedes handoff. Events retain their per-delivery revocation barrier and clear queued events. No new owner-scope field is required in job-ID queries because negative responses disclose no context and authorized positive results already carry `ExportJobContext`.

The host and CLI adapters enforce the provenance-specific presence rules after Taut decode and before privileged lookup or scheduling. Generated Python, Rust and TypeScript bindings express the fields but do not establish authorization. The reference semantic validator checks presence and denial echo against the originating request; host adapters run it before send and receiving clients after decode. Complete response indistinguishability, current grants and the shared serialization fence require host conformance tests.

## 4. Closure and compatibility proof

The gate must exercise two governed callers A and B in one project. Both can create exports; B cannot act in A's owner scope. In isolated stores or controlled state transitions, submit a byte-identical denied request against A's live, retired and unused occupancy states and compare the **complete** acknowledgements. Repeat for valid and intentionally invalid payloads; B starts no work. When the three probes use different request IDs, require each acknowledgement to echo its own request exactly and compare all non-echo denial fields. With B's own scope, the same request IDs have independent acceptance/replay/retirement semantics. A's exact replay, changed-payload conflict and retired retry retain their original outcomes after host reopen and restart. An explicitly delegated caller gains the full historical scope visibility; revoking that grant restores denial before any ID lookup or disclosure.

Repeat the live/retired/unused probes through `export.lookup`, status, events and cancel where applicable; test null negative payload and diagnostic fields. Pause a delegated lookup or submit after preliminary grant approval, revoke the grant, accept a new job, then resume the probe: it must reveal no post-revocation occupancy. Pause status and cancel after preliminary grant approval, revoke, and resume against both a known and unknown job ID; require identical unavailable envelopes, no snapshot or terminal state and no cancellation effect. Repeat with a terminal transition before the final gate and after restart. Pause a new admission before commit, retire its scope, then resume: no accepted ID or work may result. Race concurrent submissions within one scope and across two scopes against one destination, including a crash between durable admission and acknowledgement. Prove one accepted job per scoped key, no duplicate execution on retry, canonical destination exclusivity, and no rollback over a newer generation. Exercise scope retirement, project deletion, restart and tombstone compaction without owner-scope ID reuse. A standalone import must round-trip with null owner scope and retain its independent offline namespace.

Regenerate the pinned Taut Python/Rust/TypeScript bindings and golden fixtures. Run schema/semantic tests and cross-language wire tests before freezing this draft. Runtime authentication, store transaction, crash-recovery and privacy-oracle tests are implementation gates; the document and generated bindings alone do not prove them.
